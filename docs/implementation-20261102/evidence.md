# G07–G08 — километраж с происхождением и подтвержденные интервалы

Проверка: 2 ноября 2026, МСК. Рабочие заявки, реальные карты/расходы, доступы и внешние документы не изменялись.

## Реализовано

- `app/mileage.py`: CSV UTF-8 / XLSX (первый лист), предварительный просмотр и подтверждение. Сопоставление по постоянному API ID либо единственному номеру, обязательно с датой и машиной. Номер не приравнивается ID. Пусто, явный 0 и ошибочное число различаются. Отрицательные/NaN/Infinity не принимаются.
- Дополнение не создает заявку и не меняет сырой API-ответ. История `mileage_observations` хранит каждую принятую версию, источник, время формирования источником с timezone, хеш файла, строку, подтвердившего пользователя и контрольный отпечаток реквизитов заявки. Дата импорта не выдается за дату актуальности.
- Более старые файлы пропускаются; тот же источник/дата/значение — no-op. Разные значения при одинаковом времени источника — конфликт, пакет не применяется. Любая некорректная строка блокирует весь пакет. Не представленные в файле заявки не удаляются.
- При подтверждении файл и состояние заявок разбираются повторно под `BEGIN IMMEDIATE`. Изменение после preview возвращает 409. Произвольные identity/revision клиента не используются: они вычисляются на сервере.
- `mileage.enrich` добавляет эффективный КМ только при совпадающих реквизитах. Изменение даты, временных границ, автомобиля, водителя, клиента или отмена требует нового источника; КМ становится неизвестным. API-sync без КМ не стирает дополнение. Полнота периода оценивается после применения дополнений, поэтому новое число изменяет fingerprint, no-op — нет.
- `app/shifts.py`: отдельные фактические интервалы ответственности водитель–автомобиль. Начало и конец требуют явного timezone. Это не оплачиваемая смена, не моточасы и не сумма длительностей заказов. Источник/документ и явное подтверждение обязательны. История версий и soft-delete с CAS сохраняются.
- Пересечения по машине либо водителю видны и блокируют распределение. Каждое достаточно точное измерение назначается целиком одной покрывающей смене либо остается нераспределенным. Дробление суточных километров по часам/выручке не выполняется. Границы суточного API учитываются по UTC+03 согласно существующему запросу провайдера; смешанные/датированные Excel-агрегаты для точного распределения не используются.
- `app/evidence_routes.py`, `app/static/evidence.js`: рабочая страница «Контроль → Километраж и смены». Чтение соответствует существующим правам общей аналитики; запись и подтверждение только руководителю, с CSRF. Ошибки/конфликты показаны пользователю. Исходные суммы/длительности заявок работают независимо от заполнения новых таблиц.

## Контракт выгрузки

CSV UTF-8 с разделителем `;` или `,`; XLSX без исполнения формул. Заголовки: `provider_id` или `number`, `date` (`YYYY-MM-DD`), `vehicle`, `km`. `provider_id` — постоянный внутренний ID API, `number` — отображаемый номер. Если переданы оба, оба должны соответствовать. `km` — сохраненное значение километража ТТ в километрах. Файл максимум 8 МБ, распакованный XLSX до 40 МБ, до 10 000 строк.

Отдельно в форме вводятся время формирования источником (например, `2026-11-02T11:00:00+03:00`) и документ/основание проверки. Нельзя подставлять время загрузки вместо неизвестного времени формирования. `mileage-template.csv` содержит только заголовок, без выдуманных рабочих значений.

## Реальный источник и конкретный оставшийся вход

В 11:03:55 МСК 02.11.2026 выполнен один разрешенный **read-only GetOrders(OrderId=51824)** через существующий транспорт и межпроцессный `sync_lock`. Получена одна запись с этим ID; среди 49 ключей нет километража, mileage или distance. Загрузка в рабочую БД не применялась. Безопасное доказательство: `mileage-source-probe.json` (только ID, время, названия полей). Чтение текущих сохраненных 2986 ответов также не нашло КМ; последнее `seen_at` 09:32:54 МСК.

Повторно проверены официальные источники:

- [API TransTrade](https://tt-ok.ru/data/api_doc/) — опубликованный список методов/ответ GetOrders не дает проверенного поля КМ или endpoint формирования отчета.
- [Переменные печатной заявки](https://tt-net.ru/help/peremennye_dlya_blanka_zayavki.html) — `$КМ$` явно представляет километраж.
- [Конструктор отчетов](https://tt-net.ru/help/konstruktor_otchetov.html) — выбранные поля и Excel-бланк. Наличие поля КМ и внутреннего ID в picker конкретной версии требует проверки на рабочем месте.
- [История изменений](https://tt-net.ru/innovations/) — описан отчет сводки по транспорту с расстоянием из поля КМ заказа; это агрегат и не замена ID-сопоставимой выгрузке каждой заявки. Подтвержденного unattended export/CLI для установленной версии в изученных документах не найдено.

Главный агент проверил доступные UI: рабочего места ТТ/remote desktop в доступных приложениях не найдено. Это не доказательство отсутствия установки в организации, но получить ее отчет из текущего окружения невозможно без адреса рабочего места или самого отчета.

**Для реальной приемки G07 нужен** новый отчет/печатное подтверждение ТТ с API ID либо номером+датой+машиной, КМ и временем формирования для 3–5 контрольных заявок (ноль и ненулевой пробег), затем пакет за нужный период. Для автономности нужен конкретный доступный штатный механизм экспорта/рабочее место установленной версии. Ручной импорт здесь обозначен как временный путь и **не закрывает автоматическое получение КМ одной кнопкой**.

**Для реального наполнения G08 нужен** подтвержденный журнал: водитель, автомобиль, начало/конец с timezone, источник подтверждения. Для распределения частей суток нужны измерения на соответствующих непересекающихся интервалах; текущая API-история суточная. Оплачиваемое время и перерывы требуют отдельного бизнес-определения. Реальные смены автоматически из заявок не созданы.

Механизмы G07/G08 проверены на известных искусственных данных. Реальные актуальные КМ и смены пока не заполнены; внешний вход остается обязательным для сквозной приемки этих показателей.

## Дополнительная регрессия асинхронной формы

Независимый review выявил гонку: запоздалый preview мог изменить повторно открытую форму; редактирование файла во время ожидания оставляло обработчик подтверждения без подготовленного файла. Исправлено в `evidence.js`: проверка экземпляра формы/открытого диалога, поколения запроса, локальные DOM-ссылки и неизменяемый снимок полей для конкретного preview/confirm. Во время подтверждения исходные поля заблокированы; запоздалое завершение не закрывает новую форму и не вызывает ее refresh. Чтение страницы также защищено от старого запроса и смены навигации/периода.

`node --test tests/test_evidence_ui.cjs` — **10 passed**. Проверяются отложенные успехи/ошибки после close/reopen, редактирование в ожидании, два запросa в обратном порядке, старый onclick, неизменность отправляемого файла, позднее завершение confirm, закрытый диалог с сохраненным DOM, восстановление после ошибки и возврат на ту же страницу. Это содержательные JS-регрессии, не замена живой браузерной приемке.

## Прямые адреса и видимый период

При браузерном обходе обнаружен 404 при прямом открытии/перезагрузке `/control/evidence`, хотя переход SPA работал. В существующий серверный allowlist добавлен только этот действительный адрес. Изолированный HTTP-тест проверяет все 24 текущих пункта меню, повторный GET нового адреса с query, HEAD, загрузку скрипта и сохранение 401 для защищенного API/404 для неизвестных адресов. Рабочий сервис этим тестом не запускается и не изменяется.

Список дополнений КМ фильтруется видимым периодом страницы; скрытые фильтры машины/водителя, оставшиеся от статистики, на него не влияют. После исправления: **21 Python + 11 JS passed** в `test_evidence.py` / `test_evidence_ui.cjs`. Перезапуск проверочного экземпляра и повторная живая проверка адреса выполняются главным агентом.
