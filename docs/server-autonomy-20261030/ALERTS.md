# Предупреждения об обновлении данных

Модуль `app/alerts.py` отделяет временный сбой запроса от длительной проблемы. Отдельной автоматизации Codex нет. Предупреждения формирует работающий процесс обновления, а веб-приложение может вычислить отсутствие его сигнала даже после остановки процесса.

## Что считается проблемой

- Источник не обновлялся успешно **15 минут** либо столько же продолжается ошибка. Успешные старые значения не считаются свежими из-за очередной попытки запроса.
- После первого запуска источник пока ни разу не ответил: время ожидания сохраняется, повторные попытки и перезапуск не обнуляют его.
- От ожидаемого процесса обновления нет сигнала **90 секунд**. Сайт при этом может открываться с прежними данными.
- Повреждён или недоступен журнал предупреждений либо некорректно настроена внешняя доставка.

Загрузка пропущенных дней показана отдельно как очередь, без объявления её ошибкой. Краткий сетевой сбой с последующим успешным обновлением не создаёт инцидент. Отключение источника закрывает предупреждение, но не выдаётся за успешное восстановление связи.

## Поведение и сохранность

Инцидент сохраняется в закрытом `FLEET_DATA/alerts-state.json` с правами `0600`. Запись атомарная, с синхронизацией файла и каталога; отправки защищены межпроцессной блокировкой. У одного продолжающегося сбоя один ID, журнал последних закрытых инцидентов ограничен 50 записями. Повреждённый журнал не затирается: видна ошибка хранилища.

По умолчанию **сообщения наружу не отправляются**. Предупреждения доступны внутри приложения. Когда администратор явно настроит внешний канал, отправляются только начало длительного инцидента и восстановление. На каждом пятиминутном обновлении сообщения не повторяются. Неотправленное сообщение о кратковременном уже закончившемся инциденте убирается из очереди. Если источник снова недоступен, запоздалое сообщение о прежнем восстановлении также отменяется.

Неудачная доставка повторяется с задержкой от 60 секунд до часа. Очередь переживает перезапуск; за один проход отправляется не более одного сообщения. При аварийной остановке между фактической отправкой и сохранением её результата получатель может получить повтор — SMTP и Telegram не дают общего контракта атомарности с нашей локальной базой. Это ограничение внешней доставки, а не повторный импорт деловых записей.

Уведомления содержат только название источника, общий смысл проблемы и время по МСК. В них нет заявок, сумм, клиентов, исходных ошибок провайдера, адресов кабинетов с токенами или реквизитов подключения. Ответы и исключения почтового/Telegram-сервера также не показываются пользователю и не сохраняются в журнале предупреждений.

## Настройка внешнего канала

Получателя и канал выбирает владелец приложения. Пока они не указаны, не следует включать отправку. Настройки не меняют реквизиты ТТ, ГЛОНАСС и топливных поставщиков.

Файл `FLEET_DATA/alerts-config.json` необязателен. Создаётся администратором, вне Git, с правами `0600`. `enabled` должен быть именно `true`, чтобы отправка была разрешена. Файл с доступом для других пользователей блокирует отправку. Пороги можно задать без включения внешнего канала:

```json
{
  "enabled": false,
  "stale_after_seconds": 900,
  "heartbeat_stale_seconds": 90,
  "retry_seconds": 60
}
```

Допустимые пороги: устаревание источника 300–604800 секунд, отсутствие сигнала 15–3600 секунд, исходная задержка доставки 30–3600 секунд. Некорректные числовые значения заменяются безопасными значениями по умолчанию.

### SMTP

Пример ниже **отключён** и использует несуществующие адреса `.invalid`. Для включения нужны подтверждённые владелец/получатель, параметры почтового сервиса и пароль в окружении службы:

```json
{
  "enabled": false,
  "channel": "smtp",
  "smtp": {
    "host": "smtp.example.invalid",
    "port": 465,
    "security": "ssl",
    "username": "account",
    "password_env": "FLEET_ALERT_SMTP_PASSWORD",
    "from": "fleet@example.invalid",
    "to": ["owner@example.invalid"]
  }
}
```

Поддержаны `ssl` (обычно порт 465) и `starttls` (обычно 587). Проверка сертификата обязательна; незашифрованной отправки нет. Вместо `password_env` возможен `password` в этом же закрытом файле. Приложение не печатает его и не включает в ответы API. Поведение TLS соответствует [документации Python smtplib](https://docs.python.org/3/library/smtplib.html).

### Telegram

```json
{
  "enabled": false,
  "channel": "telegram",
  "telegram": {
    "bot_token_env": "FLEET_ALERT_TELEGRAM_BOT_TOKEN",
    "chat_id": "REPLACE_WITH_CONFIRMED_CHAT_ID"
  }
}
```

Получатель должен быть выбран владельцем; бот должен иметь возможность отправлять сообщения в этот чат. Вместо `bot_token_env` можно задать `bot_token` в закрытом файле. Используется только официальный HTTPS-адрес Telegram, без переходов по редиректам и отключения TLS; метод описан в [Telegram Bot API](https://core.telegram.org/bots/api#sendmessage).

## Контракт для приложения

`observe(data_dir, status, at=None, deliver=True)` сохраняет изменения и пробует доставить одно готовое сообщение. Его нужно вызывать вне критического потока, который обновляет сигнал работоспособности: внешний сервис может отвечать до истечения сетевого тайм-аута. `deliver=False` сохраняет инциденты и очередь без отправки.

`current(data_dir, status, at=None)` ничего не записывает и ничего не отправляет. Возвращает:

- `incidents`: текущие длительные проблемы;
- `recent`: последние закрытые инциденты;
- `backlog`: оставшиеся дни загрузки по источникам;
- `delivery`: включён ли канал, его тип, число сообщений в очереди, результат последней попытки и безопасный текст ошибки;
- `storage_error`: безопасное описание повреждения журнала, если оно есть.

Входной `status`: `sources` с фиксированными ключами `transtrade`, `neftm`, `rosneft`, `monitoring`; у каждого `status`, `last_success_at`, `last_attempt_at`, при наличии `error_since`, `started_at`, `configured`, `catchup.pending_days`. На верхнем уровне — `scheduler_expected`, `server_scheduler`, `heartbeat_at`, `started_at`. Времена ISO 8601 с часовым поясом. В `started_at` важно передать момент начала ожидания службы: без единого сигнала и сохранённого состояния невозможно определить длительность отсутствия процесса.

## Пределы наблюдения

Работающий веб-процесс может показать, что процесс обновления остановился. Полностью выключенный сервер не способен отправить сообщение о собственном отключении; для такого случая нужен независимый внешний контроль доступности, который здесь не создавался. Адрес/канал внешних уведомлений сейчас не выбран пользователем, поэтому живых отправок в ходе реализации не выполнялось. Тесты доставки используют только поддельные транспорты.
