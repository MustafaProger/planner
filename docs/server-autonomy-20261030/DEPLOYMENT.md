# Подготовка самостоятельной работы на сервере

Подготовлены два отдельных процесса: веб-приложение и фоновое обновление. Браузер не нужен для работы обновлений. Эта инструкция и конфигурации подготовлены локально; на удалённом сервере службы ещё не установлены и не проверены.

## Что запускается

| Процесс | Запуск | Назначение |
|---|---|---|
| Веб | `python -m app.server`, `FLEET_SCHEDULER=external` | Страницы, ручные действия и чтение состояния |
| Обновление | `python -m app.worker` | Запуск фонового цикла и контроль его работоспособности |
| Контроль сбоев | `python -m app.alertwatch`, таймер раз в минуту | Предупреждение об остановке worker независимо от самого worker |

Службы `deploy/fleet-web.service` и `deploy/fleet-worker.service` рассчитаны на Linux с systemd. Код находится в `/opt/fleet-analytics/current`, постоянные данные — в `/var/lib/fleet-analytics`, служебный пользователь — `fleet`. Переключение версии кода не должно заменять папку данных.

Обновление запускается по сохранённому расписанию. Worker проверяет работоспособность планировщика каждые пять секунд. Остановившийся планировщик или превышенное время задачи завершают worker с ошибкой, после чего systemd запускает его заново. Отказ API является ошибкой источника, а не поводом перезапускать весь процесс. Полное зависание worker обнаруживается watchdog через 45 секунд. При остановке даётся до 30 секунд на завершение текущей работы, после 40 секунд systemd прекращает процесс; полученные и сохранённые порции не откатываются.

Это следует семантике `Restart`, `Type=notify`, `WatchdogSec` и `TimeoutStopSec` из [systemd.service](https://www.freedesktop.org/software/systemd/man/latest/systemd.service.html). Сообщения готовности и watchdog передаются только локальному systemd через [sd_notify](https://www.freedesktop.org/software/systemd/man/latest/sd_notify.html). Ограничения записи и постоянный каталог настроены через [systemd.exec](https://www.freedesktop.org/software/systemd/man/latest/systemd.exec.html).

## Подготовка целевого сервера

1. Установить Python 3.12 или новее, создать отдельного непривилегированного пользователя `fleet`, разместить выбранную версию кода. Создать `.venv` на самом Linux и установить `requirements-lock.txt`. Виртуальное окружение Mac не переносить.
2. Перед любым переносом рабочей базы сделать актуальную согласованную резервную копию. Утвердить способ передачи базы, истории источников и реквизитов владельцем. Скрипты проекта не передают и не заменяют ключи самостоятельно.
3. Разместить утверждённые данные в `/var/lib/fleet-analytics`, владелец `fleet:fleet`, права каталога `0700`, базы и файлов реквизитов — `0600`. Нужны существующие `fleet.sqlite`, `session.key` и реквизиты используемых источников. Не запускать пустую новую базу вместо рабочей. История топлива и спутника находится также в JSON-файлах, одного SQLite недостаточно для полного переноса.
4. Создать `/etc/fleet-analytics/environment` по `deploy/environment.example`, без секретов. Указать фактически подключаемые источники в `FLEET_REQUIRED_PROVIDERS`. Защита запуска проверяет наличие этих файлов; она не проверяет действительность API-доступа.
5. Не переносить автоматически настройку `transtrade-network.json` с `interface: en0`: она предназначена для маршрута этого Mac. Для Linux нужен проверенный доступ с сервера к ТТ. `deploy/preflight.py` остановит запуск при обнаружении такой настройки; он не исправляет сеть и не отключает TLS.

После подготовки данных выполнить от имени служебного пользователя:

```sh
cd /opt/fleet-analytics/current
sudo -u fleet env FLEET_DATA=/var/lib/fleet-analytics \
  .venv/bin/python deploy/preflight.py
```

Проверка только читает данные. Она не создаёт пользователей, не копирует ключи и не инициализирует новую базу. При ошибке исправляется конкретная причина на целевом сервере; прежние файлы не удаляются автоматически.

Установка служб выполняется только после подготовки и проверки данных:

```sh
sudo install -m 0644 deploy/fleet-web.service /etc/systemd/system/fleet-web.service
sudo install -m 0644 deploy/fleet-worker.service /etc/systemd/system/fleet-worker.service
sudo install -m 0644 deploy/fleet-alerts.service /etc/systemd/system/fleet-alerts.service
sudo install -m 0644 deploy/fleet-alerts.timer /etc/systemd/system/fleet-alerts.timer
sudo systemd-analyze verify /etc/systemd/system/fleet-web.service /etc/systemd/system/fleet-worker.service /etc/systemd/system/fleet-alerts.service /etc/systemd/system/fleet-alerts.timer
sudo systemctl daemon-reload
sudo systemctl enable --now fleet-worker.service fleet-web.service fleet-alerts.timer
```

Если каталоги отличаются от указанных выше, сначала изменить обе unit-конфигурации и файл окружения согласованно. Не запускать дополнительный scheduler через сторонний WSGI launcher: службы уже используют явные точки входа.

Приложение слушает только `127.0.0.1:8765`. Доступ извне оформляется отдельно через HTTPS reverse proxy с согласованным доменом и настройками приложения. Открывать порт приложения в интернет вместо настройки HTTPS не требуется. Настройки DNS, сертификатов, домена и доступов этой работой не изменялись.

Пример — `deploy/nginx.example.conf`: домен и пути сертификатов намеренно нерабочие, их заменяет ответственный за развёртывание. Перед подключением проверить конфигурацию через `nginx -t`. TLS настраивается по [документации nginx](https://nginx.org/en/docs/http/configuring_https_servers.html); [proxy_cookie_flags](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_cookie_flags) добавляет защищённую передачу cookie через HTTPS. Нужен nginx 1.19.3 или новее. Не включать пример с фиктивными путями на действующем сервере.

## Проверка после установки

```sh
sudo systemctl status fleet-web.service fleet-worker.service fleet-alerts.timer
sudo -u fleet env FLEET_DATA=/var/lib/fleet-analytics \
  /opt/fleet-analytics/current/.venv/bin/python -m app.health
sudo journalctl -u fleet-worker.service -n 100 --no-pager
```

`app.health` читает `refresh-heartbeat.json` и возвращает код 1 при отсутствии/устаревании подтверждения работы, остановке или превышении срока задачи. Успешный ответ этой проверки означает, что механизм обновления работает; свежесть каждого API, неполная история и ограничения поставщика проверяются отдельно в интерфейсе. Доступный сайт сам по себе не доказывает, что worker жив.

Перед передачей заказчику проверить на отдельной копии данных: остановку worker, перезагрузку сервера, недоступность одного API, переход месяца и восстановление после нескольких пропущенных дней. После запуска очереди должны продолжаться с сохранённого места, остальные источники — обновляться независимо, записи — не удваиваться.

Полностью выключенный сервер не способен отправить собственное предупреждение. Для такого случая требуется отдельная внешняя проверка доступности. Выбор и подключение внешнего адресата согласуются отдельно; инструкция не создаёт внешнюю автоматизацию и не отправляет сообщения.

Остановка только worker обнаруживается локальным `fleet-alerts.timer`, даже если служба обновления не проходит предварительную проверку запуска. Первый контроль — через 30 секунд после загрузки, затем раз в минуту; сам observer не зависит от worker. Он сохраняет время первого обнаружения, поэтому новые короткие процессы не сбрасывают задержку предупреждения. Observer и worker используют общий журнал и блокировку для защиты от повторов. Внешняя отправка выключена до явного подключения канала в закрытом `alerts-config.json`; без него сохраняются предупреждения внутри приложения. Успешное восстановление отправляется только после ранее доставленного предупреждения.

Периодический запуск задан сочетанием `OnBootSec` и `OnUnitActiveSec` по [systemd.timer](https://www.freedesktop.org/software/systemd/man/latest/systemd.timer.html); точность запуска допускает отклонение до пяти секунд. Если таймер включён позднее 30 секунд после загрузки, первая проверка запускается сразу.

## Резервная копия и обновление версии

Согласованную SQLite-копию можно получить без остановки чтения базы:

```sh
sudo -u fleet /opt/fleet-analytics/current/.venv/bin/python \
  /opt/fleet-analytics/current/deploy/backup.py \
  --data /var/lib/fleet-analytics \
  --destination /private-backup/fleet-before-release.sqlite
```

Папка назначения должна уже существовать, принадлежать служебному пользователю и иметь права `0700`. Назначение должно быть новым: существующий файл не перезаписывается. Скрипт проверяет целостность и копирует только SQLite. Это не полная резервная копия приложения: `neftm-history.json`, `rosneft-history.json`, `monitoring-history.json`, данные очередей и реквизиты хранятся отдельно. Для полного восстановления нужен согласованный снимок постоянного каталога в утверждённое закрытое хранилище; порядок копирования секретов не задаётся автоматически.

При обновлении сначала дождаться завершения активных задач или штатно остановить обе службы, затем сделать резервную копию, переключить код, проверить зависимости и preflight, запустить службы. Старую базу поверх новой не восстанавливать: это уничтожит последующие изменения. План обратного перехода должен учитывать изменения схемы и новые записи отдельно от возврата прежнего кода.
