**Нужно:** один датированный актуальный итог/матрица готовности с последней согласованной областью; на старых отчетах явная пометка «исторический снимок до …» и ссылка вперед. ### F02. Прежний браузерный тест sidebar не воспроизводится как зеленый

Обычный `require.resolve('playwright')` из проекта дает `MODULE_NOT_FOUND`. `load_workspace_dependencies` нашел bundled `playwright` и `playwright-core` в `/Users/mustafa/.cache/codex-runtimes/codex-primary-runtime/dependencies/node/node_modules`; пакет `@playwright/test` для этого сценария не нужен, файл использует `node:test`.

С bundled `NODE_PATH` и отдельным Chrome запущен исходный `tests/test_sidebar_scroll.cjs`. Первый общий диагностический процесс остановлен по 45-секундному пределу во время второго сценария. Дополнительный одиночный desktop запуск завершился exit 1: **`locator.click: Timeout 30000ms exceeded`, ожидание `[data-tab="transtrade"]`, `tests/test_sidebar_scroll.cjs:29:49`**. Точный вывод — в `02-browser-test-environment.json`; измеренная внешняя длительность одиночного процесса составила 563,696 с, что отдельно от 30-секундного locator timeout (причина различия не устанавливалась). Сам тест перехватывает **все** запросы к `fleet.test`; он не проверяет production и не использует рабочую БД. Тест завершен, production-процессы не останавливались.

Селектор устарел: файл кликает `[data-tab="transtrade"]`, тогда как текущий `ui.js` перестроил меню и этого пункта больше нет. Исполнение дошло именно до данного клика. Это **не доказанный дефект прокрутки приложения**. Прежний живой scroll/Back был проверен отдельно, но не эквивалентен всем rerender/Back/Forward сценариям файла.

**Нужно:** воспроизводимый launcher зависимости и актуальные mocked API/маршруты/селекторы при сохранении смысла scroll → navigation → rerender → Back → Forward, desktop и mobile. Не удалять тест или ослаблять проверку ради зеленого результата; не устанавливать новые зависимости в production без необходимости. Bundled runtime может дать быстрый локальный путь, а репозиторий должен объяснять переносимый запуск.

**Приемка:** оба сценария проходят на изолированной среде, без реальных учетных данных/поставщиков; проверка действительно достигает всех заявленных переходов. Финальный живой smoke нового чата отдельно проверяет нужные экраны, не называя мок-тест полномасштабной пользовательской приемкой.

### F03. Достоверные рабочие факты и выбранный канал еще нужны

Это не новая ошибка кода. Для полного результата по исходному замыслу требуются: действительные интервалы/основания смен, история карт с датами/машинами, решения по конкретным спорным назначениям, расходы/статусы и проверенные периоды. Точные текущие количества надо получить read-only с VPS; архивный локальный snapshot нельзя назвать свежим. Для G12 нужен явный получатель/канал, после чего отдельно проверяется доставка. Код/формы не дают этих фактов и не разрешают отправку.

Следующий исполнитель может подготовить актуальную очередь действий и проверить готовность существующих форм на fixtures. Он не должен заново писать те же модули или назначать карты/смены/расходы по вероятности. КМ ТТ остается deferred до отдельного решения о продолжении подключения.

### F04. Свежая операционная приемка имеет ограниченный охват

Public health и совпадение четырех assets доказаны сейчас; authenticated source state и серверный Python отдельно не проверялись. В следующем чате достаточно точного read-only снимка источников/очереди/версии и необходимых браузерных сценариев. Мутационные сценарии — в изолированной копии с отключенными providers/scheduler. Не нужно ради аудита включать второй production worker, менять DNS/пароль или перезагружать VPS.
