# Исторические показатели ГЛОНАССсофт — 27 октября 2026

## Что подключено

Источник — `https://monitoringtransporta.online/api/v3/`, аккаунт и токен прежней интеграции. Документация: https://glonasssoft.ru/wiki/metody-api-dlya-raboty-s-glonasssoft.

История загружается из двух методов чтения:

- `POST vehicles/mileageAndMotohours`: пробег в километрах, моточасы в секундах → деление на 3600.
- `POST vehicles/fuelConsumption`: расход топлива `fuelConsumption`.

Первый период выбран по существующим фактическим заявкам: 1–31 августа 2026. Все 19 объектов имеют уникальный госномер, совпадающий со справочником. Нечёткий поиск имён, автоматическое распределение по водителям и привязка к ресурсам партнёров не применяются.

## Порции и продолжение

Каждый запрос содержит одни завершённые сутки и максимум три объекта. Границы `00:00:00` — `00:00:00` следующего дня, `timezone: 3`, `sampling: 86400`. Для топлива также всегда запрашиваются одни сутки: этот метод игнорирует sampling. Период запуска — до 93 завершённых дней; текущий день нельзя ошибочно сохранить как полный.

Запросы выполняются последовательно с ограничением частоты в клиенте. Если пакет не получен или не прошёл проверку структуры, он разделяется на отдельные машины, каждая запрашивается один раз. Ошибка авторизации останавливает работу без перебора/повторения входов для каждой машины. После девяти неудавшихся машино-дней/метрик задание останавливается с сохранением прогресса.

Оба типа показателей сохраняются независимо, по ключу `vehicleId:date`. После каждой порции атомарно обновляется `data/monitoring-history.json`; файл вне Git с правами 0600. Повторный запуск без флага обновления пропускает сохранённые порции, запрашивая только недополученные. Флажок «Повторно запросить сохранённые дни» позволяет запросить период заново. Пустой ответ при обновлении не стирает ранее полученные показания.

`data/monitoring-history-job.json` хранит прогресс, период и состояние. Файловая блокировка защищает от двух одновременно работающих загрузчиков, включая разные процессы. После прерывания приложения интерфейс предлагает продолжить; автоматическое расписание не создавалось. Число порций в интерфейсе — число машин × дней × 2 группы показателей; одна HTTP-порция может закрыть до трёх таких единиц.

## Качество данных и расчёты

- Ответ проверяется по идентификаторам, уникальности и точным суточным границам. UTC-границы при наличии смещения переводятся в МСК.
- Неконечные/отрицательные значения не используются. Отсутствующий объект или период — отсутствие показаний.
- Все нулевые пробег/накопительные счётчики не подтверждают наличие телеметрии: значения остаются неизвестными. При положительном накопительном счётчике нулевой суточный пробег/моточасы допустимы.
- Если расход и начальный/конечный уровни топлива полностью нулевые, ответ консервативно считается «Нет подтверждённых показаний». Это не утверждение об отсутствии датчика. Положительный расход либо ненулевой уровень позволяет использовать полученный расход, включая ноль.
- Нулевой расход при пробеге больше 1 км помечается «Нулевой расход при движении — проверить» и исключается из производных показателей топлива. Исходный ноль сохраняется в кэше. Это консервативное правило качества, не утверждение о причине ошибки провайдера.
- API заменяет одноимённый показатель Excel за ту же машину и дату. Суммирования двух источников за один день нет. При отсутствии числового значения API остаётся Excel, с явным источником показателя. Исходная Excel-запись в SQLite не перезаписывается.
- Моточасы — время работы двигателя. Прежний `hours` из Excel сохранён отдельно как длительность спутникового интервала. Моточасы не вычитаются из часов рейсов и не считаются рабочим временем водителя.
- Сверка — по автомобилю и дате начала заявки; спутник охватывает полные сутки. Это не точное распределение километров и топлива по каждому рейсу. Ночные рейсы могут переносить расхождение между датами.
- Расход и моточасы суммируются только по дням с показаниями, рядом показывается число таких дней.
- `л/100 км = Σ расхода / Σ пробега × 100` только по общим дням с обоими показателями. Это не среднее дневных коэффициентов.
- Итоговая разница месячного пробега не рассчитывается, если отсутствует пробег в какой-либо день рейсов. Суточные неизвестные показатели остаются `null`, а не нулём.
- Цена/стоимость топлива и распределение по водителям не выводятся из литров предположениями. Финансовые суммы заявок не изменены.

## Интерфейс и доступ

- `/integrations/monitoring`: период, продолжение/повторная загрузка, прогресс, таблица покрытия и сопоставлений.
- `/analytics/statistics`: моточасы, литры, л/100 км, число дней с показаниями и источник пробега.
- `/analytics/reconcile`: суточные показатели рядом с заявками, источники пробега/моточасов и состояние топливных данных. Экспорт CSV включает новые поля.
- GET `/api/monitoring/history` и POST `/api/monitoring/history/sync` доступны руководителю; POST требует CSRF и возвращает 202, не удерживая HTTP-запрос на время всей загрузки. Расчётные отчёты используют существующие права приложения.
- Сервер продолжает слушать только localhost. Верхняя шапка на компьютере и ранее исправленная прокрутка не менялись.
