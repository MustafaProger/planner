# Получение КМ заявки ТрансТрейда — исследование для этапа 5

Дата: 02.11.2026. Это выбор технического пути, не реализованная интеграция и не подтверждение актуальных километров в рабочей базе. Приложение, БД, доступы и внешние заказы не изменялись; аутентифицированные API не вызывались.

## Установлено

1. В `app/transtrade.py:132–154` нормализатор явно создаёт `km=None`. Все 2 986 текущих сохранённых ответов не содержат поля КМ по проверке агента 3 (`03-probes.json`). Поэтому недостаточно поменять отображение или считать спутник пробегом ТТ. Более того, если поставщик позднее добавит поле, действующий нормализатор всё равно его не использует без доработки.
2. Опубликованный сейчас список методов и пример ответа `GetOrders` не предлагают поля километража или метода формирования отчёта. Документированы фильтры `OrderId`, диапазоны ID и дат; `ID` и `Number` — разные поля. Частный расширенный контракт этим не исключён. [Официальная API-документация](https://tt-ok.ru/data/api_doc/).
3. Значение существует в исходном продукте. В справке описано поле километража на вкладке расчёта стоимости. Возможность вычислить расстояние между адресами — отдельное действие; она не доказывает, что поле заполнено фактическим измерением. Для нашей задачи нужен именно сохранённый КМ, который логист вводит по принятому процессу. [Создание заказа](https://tt-net.ru/help/sozdanie_zakaza.html).
4. Официальный конструктор создаёт табличные шаблоны по выбранным заказам, позволяет выбирать поля, задавать Excel-бланк и повторно формировать отчёт. Опубликованный screenshot вкладки «Заказ» показывает номер заказа, начало/окончание и автомобиль. КМ на этой вкладке не виден; доступность нужного поля в других вкладках именно рабочей базы ещё требуется проверить. Внутренний API-ID в screenshot не показан. [Конструктор отчётов](https://tt-net.ru/help/konstruktor_otchetov.html), [проверенное изображение](https://tt-net.ru/help/IMG/drex_konstruktor_otchetov_custom_3.png). Копия изображения: `05-report-fields.png`.
5. Для печатной заявки явно документирована переменная `$КМ$`; также доступны `$НОМЕР$`, `$СЕЙЧАС$`, даты и автомобиль. Это дополнительный официальный способ вывести сохранённое поле, если требуемое поле конструктора не удастся выбрать. Номер печатного документа сам по себе не доказывает равенство API-ID. [Переменные бланка заявки](https://tt-net.ru/help/peremennye_dlya_blanka_zayavki.html).
6. Предоставленная книга уже содержит исторический КМ: `Статистика 17.09.2026.xlsx`, «ТрансТрейд», колонка M; в прошлой проверке для 51025 было 93, для 51824 — 0. Это датированное доказательство старого значения, а не текущего. Исходная запись сохранена как `legacy_snapshot` при обновлении API (`app/transtrade.py:206–208`); её нельзя незаметно вернуть в актуальный показатель.

## Рекомендуемое решение

Сделать единый слой наблюдений метрик заявки, который умеет принять проверенное поле API или дополнительную выгрузку ТТ. В основной строке заявки сохранять принадлежность API, деньги, категории и ID; значение пробега должно ссылаться на отдельное наблюдение с происхождением. Этот механизм можно реализовать независимо от поставщика уже сейчас и проверить на искусственных данных и исходной исторической книге. Но для включения **актуальной** сверки нужен новый источник КМ, а не только готовый код.

### Путь A: подтверждённое поле API — основной автоматический вариант

- Перед реализацией проверить свежий raw той же контрольной заявки и текущий документированный контракт. Не перебирать недокументированные имена методов и не угадывать смысл нового числового поля по слову `km`.
- После установления точного имени, единиц и семантики пустого значения добавить явный mapper в `normalize`. `None`, отсутствующее поле и подтверждённый `0` различаются; отрицательное/нечисловое/бесконечное значение не принимается. Сохранять raw, время чтения и hash ответа.
- Обновить `sources.km`, фактический счётчик `without_km` (сейчас он равен длине списка, `transtrade.py:234`), сведения о доступности поля и тесты. Повтор без изменений не должен создавать новые записи или снимать полноту.
- Этот вариант закрывает автоматическую загрузку лишь после реальной сверки нескольких заявок с исходным экраном ТТ. В текущем исследовании такого поля не найдено; объявлять путь A уже подключённым нельзя.

### Путь B: отдельный импорт текущего отчёта — практически реализуемый резерв

1. Проверить на существующем рабочем месте ТТ доступный шаблон отчёта с сохранённым КМ. Минимальные столбцы: явный внутренний ID **если доступен**, отображаемый №, начало/окончание, машина, КМ; экспортируемый период и время формирования записывать как метаданные пакета. Если конструктор не отдаёт КМ, проверить официальный бланк с `$КМ$` и теми же контрольными реквизитами. Создание/изменение общего шаблона — отдельная настройка источника, в этом исследовании не выполнялась.
2. В планировщике принимать небольшой CSV/XLSX как дополнение метрик, **не** запускать полный повторный импорт двух книг и **не** создавать вторые заявки. Сначала показывать предварительный результат: найденные, без соответствия, неоднозначные, конфликтующие и устаревшие строки. Подтверждение относится к конкретному разобранному пакету с hash файла.
3. Наличие цифрового «№ заказа» не означает `Number == ID`. Предпочитать явно подтверждённый `provider_id`. Если экспорт содержит только отображаемый номер, строить кандидатов по номеру и дате, а машину/начало/окончание использовать как контроль; применять лишь при единственном подтверждённом соответствии. Если существующий режим нумерации использует API-ID в отображаемом номере, это нужно проверить и сохранить как настройку источника, а не вывести из сходства цифр. Неоднозначные строки помещать в очередь ручного сопоставления с конкретной API-заявкой; не объединять по ФИО или сумме.
4. Для каждого принятого наблюдения хранить минимум `provider_id`, `metric=order_km`, `value`, `unit=km`, `source_type`, `captured_at`, `exported_at` (если известно), hash исходного файла, строку/лист, исходный номер, кто подтвердил сопоставление и наблюдавшийся fingerprint даты/машины/заявки. Не выдавать время импорта за дату актуальности данных поставщика.
5. Операция идемпотентна по пакету и содержимому наблюдения. Новый отчёт создаёт новую версию значения, старый остаётся в истории. Полученный позднее старый файл не вытесняет более свежую версию. Отсутствие строки в файле ничего не удаляет. API, не содержащий КМ, не стирает дополнение. При изменении даты/машины/смысла заявки после дополнения значение требует проверки, а не автоматически переносится на новый факт.
6. В отчёте явно видны источник и дата КМ. Исторический Excel доступен только как историческое наблюдение; для текущего режима без свежего подтверждения остаётся «неизвестно». Дополнение не повышает автоматически полноту всей выдачи ТТ: охват КМ, охват списка и бизнес-подтверждение периода — разные утверждения.

Этот резерв уменьшает ручной ввод до выгрузки и подтверждения пакета и не требует заново вводить заявки. **Ручная выгрузка не выполняет требование полностью автоматического обновления.** Для автономной доставки такого пакета нужен проверенный механизм рабочего места: официальный способ выгрузки по расписанию либо отдельный авторизованный read-only UI-процесс. Их наличие в текущей конфигурации не установлено. Не следует обещать серверное формирование отчёта на основании существования кнопки в Windows-приложении.

### Путь C: подтверждение одиночного значения — только исключение

Если текущий отчёт получить нельзя, уполномоченный сотрудник может сверить конкретную заявку в ТТ и внести КМ как отдельное подтверждённое наблюдение со ссылкой на ID, временем и основанием. Эта форма не должна менять заявку в ТТ или позволять выдавать норматив/спутник за введённый логистом КМ. Подходит для небольшого количества исключений и проверки основного адаптера, но не закрывает ежедневную автоматизацию всего парка.

## Приёмка адаптера

- Один API-ID + повтор того же пакета → одна активная заявка и одно наблюдение; суммы/категория/история исходной заявки сохранены.
- `0`, пусто, отсутствующая колонка, `NaN`, отрицательное число и дробное `93,5` обрабатываются различно и предсказуемо; только документированное неотрицательное значение становится пригодным.
- Два заказа с одинаковым отображаемым номером, несовпадающая машина или отсутствующий ID не приводят к автоматическому слиянию.
- Старый Excel с 93 км показывается с датой источника и не объявляется текущим. Новый пакет с 101 км сохраняет обе версии и показывает новое значение только после принятия.
- API-обновление без километража не стирает принятое дополнение; API-обновление с подтверждённым полем создаёт отдельное наблюдение и понятное правило выбора актуального источника. Конфликт двух источников виден.
- Перенос заявки на другую дату/машину после дополнения требует пересмотра охвата и не переносит прежнее значение молча. Неизменный повтор чтения не меняет подтверждённость.
- На одинаковой машине и дне проверить КМ ТТ, КМ спутника и знак разницы; оба исходных источника раскрываются. При недостатке хотя бы одной стороны дельта неизвестна. Несколько заявок не размножают суточный спутниковый пробег.
- Файл неполного периода не удаляет отсутствующие заявки и не помечает весь период полным. Ошибка парсинга откатывает пакет целиком.

## Минимальный внешний вход для фактического включения

Достаточно одного **нового** сформированного источником отчёта с КМ и проверенным соответствием 3–5 контрольных заявок API-ID, включая ноль и ненулевое значение; затем полного пакета нужного периода. Альтернатива — подтверждённое имя/семантика нового поля API и свежий ответ этих же заявок. Для автоматизации резервного экспорта требуется конкретное доступное рабочее место/официальный механизм, а не новые права или закупка, предполагаемые агентом.

Ни один из этих внешних входов в текущем исследовании не получен. Найден конкретный путь реализации без выдуманного километража; бизнес-результат «все актуальные КМ поступают автоматически» остаётся неподтверждённым до испытания источника.

## Дополнительная диагностическая заметка

Публичная документация доступна через web-инструмент. Загрузка её статического screenshot обычным локальным HTTPS-запросом завершилась TLS timeout; тот же публичный GET через `curl --interface en0` завершился успешно примерно за 0,1 с. Сетевые настройки не изменялись. Это локальное наблюдение, не доказательство причины ошибок Роснефти/Нефтьмагистрали/ГЛОНАСС и не рекомендация автоматически менять маршруты всех коннекторов.
