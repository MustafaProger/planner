## G01. Пути Excel и воспроизводимость

Точки: `app/importer.py:6,29`, `app/server.py:5,20–41,207–226`, `tests/test_app.py:1–14`. Сейчас модуль импортирует константу `SOURCE` по значению, поэтому простая замена одного глобального объекта уже после импорта дает разные пути у импортера и сервера.

Рекомендуется один resolver исходных книг, вызываемый при необходимости чтения, с приоритетом: явно переданные пути → документированная конфигурация (`FLEET_EXCEL_DIR` либо два индивидуальных пути) → необязательная локальная конфигурация вне Git. Путь конкретного пользователя не должен становиться новым зашитым дефолтом. В локальной конфигурации этой установки допустимо явно указать уже предоставленный `/Users/mustafa/Desktop/планировщик`; это настройка, а не логика продукта. В `server.py` обращаться к resolver, а не импортировать изменяемую `SOURCE`.

Существующая заполненная БД должна запускаться без доступности первоначальных книг. Для пустой БД заранее проверить существование/формат пары книг и вернуть конкретное сообщение настройки; не оставить наполовину выполненный первый импорт. Более широкий вариант — экран первой загрузки пустой рабочей базы, но он не нужен для минимального исправления. Multipart-импорт уже существует и должен сохранить приоритет перед локальными путями.

Тесты разделить по назначению. Автономные проверки API/прав/расчетов используют маленькие синтетические XLSX/данные во временной папке. Проверка сохранности настоящих 996 строк и контрольных сумм остается отдельной обязательной проверкой на предоставленных книгах, с явными путями/конфигурацией. Не переносить клиентские книги в публичный Git и не подгонять синтетические строки под реальные контрольные суммы. Не скрывать прежние 20 ошибок простым `skip` всего модуля. На этом компьютере штатный запуск с сохраненной локальной конфигурацией должен пройти без Python-подмены глобальных переменных.

Приемка: обычный pytest с документированной конфигурацией проходит; изменение cwd не ломает импорт; новая копия с явными источниками импортируется; без источников сообщает настройку без фиктивных данных; заполненная БД не требует Excel; загрузка пары книг через форму и повтор не теряют ручные записи. Контроль исходника сохраняет 13 724 319,06 ₽ выручки, 6 930 671,46 ₽ выплат и 99 197 км всех нумерованных строк (это суммы книги, не суммы текущего API).

## G02. Подтверждение полноты конкретного набора

Точки: `workspace.schema/save_extra/create_records/edit_record/ingest/dataset`, `reports.coverage/comparison`, `transtrade.apply` около строки 225, форма полноты в `workspace.js:73–75`.

**Предпочтительный вариант — отпечаток содержательных данных подтверждаемого интервала.** При подтверждении хранить `source`, начало/конец, `checked_at/by`, версию алгоритма и `checked_fingerprint`. Отпечаток строится из упорядоченных стабильных ID и бизнес-полей строк этого источника: даты/начала/конца, сущностей, категории/состояния/отмены/исключения, денежных сумм, км/часов, признаков спорного назначения. Он не должен зависеть от `synced_at`, порядка ответа API, текста технического сообщения или времени обычного чтения. Для полного пустого периода отпечаток тоже определен и включает источник/границы.

При чтении отчета сравнивать текущий отпечаток с подтвержденным. Совпадает — подтверждение действительно; различается — «Данные изменились после проверки», дельты закрыты, прежнее подтверждение остается историческим фактом. Это покрывает ручной ввод, удаление, reimport, перенос между датами, отмену и обновления ТТ, даже если отдельная ветка записи не вызвала ручной invalidation-hook. При слиянии сущностей учитывать разрешенные стабильные ID, а не только отображаемое имя. При расширении поля, влияющего на отчет, обновляется версия алгоритма.

Форма подтверждения получает отпечаток именно просмотренных данных. POST в той же транзакции повторно вычисляет его; если между просмотром и подтверждением данные поменялись — конфликт и перечитывание. Нельзя автоматически подтвердить новую версию только потому, что пользователь нажал старую кнопку. Старые записи `coverage`, у которых отпечатка нет, не следует молча превращать в проверку нынешних данных: показать необходимость однократной повторной проверки. Сейчас рабочих `coverage` нет, но миграция все равно должна корректно обрабатывать их в fixtures.

Альтернатива — содержательные ревизии по `(source, date)` с накоплением затронутых старых/новых дат. Она быстрее при большом объеме, но требует доказать участие всех путей записи. Не использовать единственную глобальную ревизию: ноябрьское изменение не должно снимать проверку августа.

**Обнаружен и обратный дефект существующего механизма:** `transtrade.py:225–230` снимает полноту при любом успешном refresh пересекающегося периода, даже когда все записи `unchanged`, из-за условия `overlap OR changed_dates`. После перехода на единый механизм убрать этот безусловный сброс; неизменный опрос каждые пять минут не должен делать подтверждение бесполезным.

Приемка: подтвердить период → create/edit/delete/reimport/TT-change внутри него → статус устарел; перенос проверяет обе даты; изменение вне периода не влияет; два no-op API/Excel-повтора не снимают подтверждение; отрицание/удаление подтверждения работает; попытка подтвердить устаревший preview отклоняется; нулевые/пустые полные периоды отличны от неподтвержденных. Изменение заметки, не влияющей на цифры/принадлежность события, не вызывает бессмысленный сброс.

## G03. Марка и принадлежность без смешения сущностей

Точки: `analytics.filtered/report/aggregate`, `workspace.catalogs/resolve_row`, статистика `main.js:58`, фактические переопределения `ui.js` и CSV. Не использовать один неоднозначный ключ `company` для четырех разных понятий.

Ввести явные разрезы `vehicle_brand` («Марка автомобиля»), `vehicle_company` («Принадлежность автомобиля»), `driver_company` («Компания водителя»), при необходимости уже имеющийся `resource_type` («Вид ресурса: автомобиль/партнер/служебное»). Существующий `carrier` остается «Исполнитель заявки». Клиент остается клиентом. Группировать по стабильной сущности/нормализованному справочному атрибуту, перед агрегацией добавляя его к каждой исходной записи **один раз**. Отдельные фильтры используют те же значения и тот же prepared dataset, что таблица, детали, итоги и экспорт.

Не угадывать принадлежность из ФИО, номера, похожего названия перевозчика или API `Firm`. В текущей модели поля каталога изменяются без исторической шкалы. Поэтому результаты по ним явно называются «по текущему справочнику», а неизвестные значения остаются группой «Не указано». Если понадобятся исторические разрезы, отдельная датированная история принадлежности заполняется только доказанными сведениями; задним числом автоматически ее не достраивать. Наличие новой группировки не обещает такой истории.

Неподдерживаемый `group` лучше возвращать как ошибку валидации с перечнем допустимых значений, а не молча превращать в `vehicle`. Если нужна совместимость со старым UI, оставить только явно известные legacy aliases с тестом. Не добавлять новые страницы: достаточно выбора разреза в существующей статистике.

Приемка: две машины одной марки дают сумму обеих без удвоения; один водитель на двух машинах не получает обе полные суточные телеметрии; разные компании машины/водителя/исполнителя различимы; неизвестное не исчезает; totals исходной выборки одинаковы во всех группах; фильтр+детали+CSV совпадают; переименование не создает новую финансовую строку; текущий атрибут не назван историческим.

## G05. Средние с явным числителем и знаменателем

Доказательство смысла, даже при сохраненных `#REF!`: `Статистика 17.09.2026.xlsx`, `Анализ!N3` делит `[Сумма (Руб)]` на `[Число элементов в столбце Сумма]`; `P3` делит `[Спутник(Км)]` на тот же счетчик; `R3` делит `[Сумма по столбцу Исполнителю]` на него. Заголовки N1/P1/R1 — «Ср чек», «Ср пробег», «ЗП». Формулы доступны в `02-workbook-structure.json`. Точное внутреннее DAX-поведение счета элементов не восстановлено, поэтому нельзя назвать `вся выручка / число рейсов` буквальной проверенной копией Excel.

Рекомендуется показать в существующей статистике два однозначно названных семейства через выбор метрик/детали:

| Метрика | Предлагаемая явная арифметика |
|---|---|
| Средняя сумма записи ТТ | Сумма выручки выбранных неотмененных записей / число этих записей с числовой выручкой; если часть сумм неизвестна, итог неполон и основной показатель «—» |
| Средняя выплата по записи | Сумма выплат выбранных записей / число записей с числовой выплатой; аналогичная проверка неполноты |
| Средняя выручка рейса | Выручка только строк `category=Рейс` / число этих рейсов |
| Средняя выплата рейса | Выплаты только строк `category=Рейс` / число этих рейсов |
| Средний пробег рейса ТТ | Пробег только строк `category=Рейс` / число этих рейсов, только при известном пробеге всех включенных рейсов |
| Средние часы рейса | Существующая длительность заявок / число рейсов; не переименовывать в фактическую рабочую смену |

Отдельно при необходимости можно показать «Вся выручка на рейс» = деньги всех категорий / число рейсов; это **другая** величина, а не скрытая замена среднего чека. Для сравнения с исторической Excel-формулой спутниковый пробег/число записей допустим только как буквально названный коэффициент на совпадающих машинах/датах и полном покрытии, а не «пробег конкретного рейса». При недостаточном сопоставлении он остается недоступен. Вводить все варианты обязательными видимыми колонками не требуется; сохранить понятные названия и раскрытие формулы.

Точки: `analytics.aggregate/report`, UI/CSV статистики. Внутри агрегата накапливать числитель и count каждой метрики. Общий итог считается из исходных сумм/count, никогда усреднением средних групп. Для среднего пробега спутника не повторять дневной пробег на каждую строку заказа. Ноль числителя допустим при положительном знаменателе; ноль/неизвестный знаменатель — `null`; NaN/Infinity не выдаются.

Контроль: рейсы 1000 и 2000 ₽ + доплата 300 ₽ + удержание −100 ₽ дают общую выручку 3200 ₽, среднюю сумму четырех записей 800 ₽, среднюю выручку двух рейсов 1500 ₽, всю выручку на рейс 1600 ₽. Эти значения не взаимозаменяемы. В выборке только удержаний нет средних на рейс. Проверить разные размеры групп, отмену, неизвестную сумму/км, фильтры и экспорт. Никаких налоговых коэффициентов/новой зарплатной формулы это решение не вводит.

## G06. Удаление с проверкой просмотренной версии

Точки: `workspace.edit_record:367–396`, `server.delete_manual:200–205`, `server.extra_delete:132–140`, `main.js.bindDelete:65`, `workspace.js:73`, дедупликация статусов в `workspace.dataset:198–205`.

1. UI передает `revision` записи, показанной пользователю, в JSON DELETE либо строго определенном conditional header. Не подгружать свежую revision незаметно непосредственно перед удалением: это обход смысла защиты.
2. Сервер проверяет тип/обязательность версии и полномочия **до любого удаления**. Отсутствующая версия не означает разрешение; конфликт возвращает 409 и предложение перечитать. Для импортированной заявки прежний запрет удаления сохраняется.
3. На уровне SQL применять условие `WHERE id=? AND revision=? AND deleted=0`, проверять, что изменилась ровно одна запись. Проверка версии в Python плюс безусловный UPDATE не дает достаточной межпроцессной гарантии при отдельном worker.
4. У объединенного статуса UI-строка может представлять `related_ids`. Возвращать клиенту состав и версии этой группы/производный token; перед удалением проверить весь набор и версии в одной транзакции. При изменении одной части или состава группы ничего не удаляется. Аналогично дополнительные сущности (`coverage`, карты, расходы) получают version-aware delete; не ограничиваться ручными планами.
5. Изменение данных и G02-полноты/аудита — одна атомарная операция. Soft-delete и существующая история не превращаются в физическое удаление пользовательских фактов.

Для связанных записей подойдет существующий SQLite transaction с получением write-lock до чтения проверяемой группы или атомарный набор compare-and-set с rollback при любом несовпадении. SQLite допускает несколько читателей, но одного писателя; `BEGIN IMMEDIATE` может получить `SQLITE_BUSY`, поэтому нужен обработанный конфликт/таймаут, а не частичный успех. Это подтверждается [официальной документацией транзакций SQLite](https://www.sqlite.org/lang_transaction.html).

Приемка: A открывает v1 → B меняет v2 → DELETE A дает 409 и сохраняет v2; после явного перечитывания разрешенное удаление v2 работает; отсутствующая/неверная версия отклонена; две конкурентные удаления не считаются двумя успехами; связанную группу нельзя удалить частично; права/CSRF и запрет импортированных заявок сохранены. Проверять отдельными соединениями/процессами, а не только последовательными вызовами одной функции.

## G07. Километраж ТрансТрейда с дополнительным источником

Подробное независимое исследование официальных возможностей: `05-tt-mileage-research.md`. Текущий документированный `GetOrders` не предоставляет проверенного поля КМ ([официальный API](https://tt-ok.ru/data/api_doc/)). В официальной справке продукта есть [километраж `$КМ$` в печатной заявке](https://tt-net.ru/help/peremennye_dlya_blanka_zayavki.html), [конструктор отчетов и Excel-бланки](https://tt-net.ru/help/konstruktor_otchetov.html). Это дает практический путь дополнительного источника; точная выгрузка КМ и внутреннего API ID установленной версии должна быть проверена на одной реальной заявке.

**Порядок вариантов:**

1. Проверить текущий официальный ответ по одной известной заявке и сопоставить с ее видимым КМ в ТТ. Если поставщик действительно добавил поле — ввести его в allowlist mapper, единицы и контрактные tests. Одного обещания поддержки недостаточно.
2. В существующей разрешенной установке ТТ проверить сохраненный/настраиваемый отчет с номером, датами, машиной, КМ и, если доступно, внутренним ID. Сформировать минимальный свежий образец через штатный отчет/документ; не изменять заявки. Поле `$КМ$` в печатном документе — подтвержденный резервный канал проверки значения, но это не доказательство, что тот же столбец уже доступен в picker отчета.
3. Реализовать **дополнение метрики**, а не повторный импорт всей базы: parser CSV/XLSX/строго определенного шаблона → preview совпадений/конфликтов → версионное хранилище измерений → read model отчета. Это уже реализуемая независимая часть. Километраж не должен создавать второй рейс и не должен жить как случайная правка raw API.
4. Для конечного автоматического режима проверить, существует ли на данной установке официальный unattended export/планировщик/CLI/документированный endpoint. Такой механизм пока **не подтвержден**. Если его нет, ручной export — временный рабочий путь получения данных, но R02 для этого показателя остается частичным. UI-автоматизация возможна только после проверки реального доступного рабочего места и условий стабильности; она не должна требовать открытого пользовательского браузера под видом серверной автономности. Нельзя выдумывать endpoint или штатную команду выгрузки.

Предлагаемая запись дополнения: `provider`, `provider_order_id`, отображаемый `order_number`, `metric=km`, числовое значение/единица, время формирования источника `source_as_of`, время загрузки, тип/хеш источника и ссылка на строку, дата/машина для контроля, состояние `verified/conflict/stale`, версия. Внешний ID приоритетен. Номер заказа не приравнивать к ID: если в экспорте только номер, разрешать сопоставление лишь с единственной существующей API-записью, проверив дату и машину; неоднозначности помещать в очередь, а не выбирать первую. Явный ручной mapping тоже хранит основание.

Приоритет источников задается явно: проверенный актуальный API metric, если появится; иначе подтвержденное дополнение с временем источника; старый Excel показывается историческим значением отдельно. Загрузка того же хеша/версии идемпотентна. Более старый export не вытесняет новый. Одинаковый timestamp с разными значениями — конфликт. API-обновление без КМ не удаляет дополнение; изменение даты/машины/идентичности заявки переводит дополнение на повторную сверку, если нарушены контрольные поля. `source_as_of` нельзя бездумно брать из mtime скачанного файла.

Отчет использует effective km с видимым происхождением/датой. Если хоть один включенный рейс не имеет проверенного показателя, полный итог и Δкм не объявляются рассчитанными; сумма известных может быть показана отдельно с покрытием. Нулевой КМ признается только как явный 0 источника, а не пустая ячейка. Не использовать спутниковый КМ и маршрутный норматив как КМ логиста.

Приемка: реальная известная заявка с известным из ТТ КМ → совпадающее дополнение; коррекция КМ в ТТ → обновление той же записи; no-op и повтор файла не дублируют; старый файл/другой заказ с тем же номером не портят новую запись; следующий штатный TT sync не стирает дополнение; общий синтетический день дает правильный знак Δкм; неполное покрытие остается явным. Автоматический режим дополнительно принимается только при двух запусках без открытого браузера/Excel и доказанном получении исправленного значения.

## G08. Подтвержденные смены и сопоставимое время

Ни начала/концы заказов, ни номер плановой смены, ни моточасы не доказывают фактически отработанную смену. Поэтому безопасное решение имеет два независимых слоя.

**Слой фактов.** Минимальная сущность фактического интервала: стабильные `driver_id`, `vehicle_id`, начало/конец с явным часовым поясом, вид времени («интервал ответственности/смены»), источник/документ/строка, подтвердивший и время подтверждения, revision. Может вводиться через отдельную форму/импорт подтвержденного табеля/журнала смен, если такой источник предоставлен. Длительность интервала — разность timestamps; длительность 27 ч сохраняется. Если бизнесу нужны оплачиваемые рабочие часы с исключением перерывов, требуется отдельное явное правило/факт перерыва; не вычитать их автоматически.

Заявки ТТ могут **предлагать** кандидаты водитель–машина–начало–конец с подписью «по заявке», но не становиться подтвержденной сменой без проверки. Несколько перекрывающихся заказов одного водителя не суммируются как длительность смены: в отдельной метрике «покрыто интервалами заявок» используется объединение интервалов, не их арифметическая сумма. Существующая сумма часов заказов сохраняется и называется соответственно.

**Слой измерений.** Для точного распределения нужен спутниковый результат на том же интервале. Существующий код запрашивает `vehicles/mileageAndMotohours` по суткам с `sampling=86400`, `timezone=3`; он не доказал точность меньших периодов. Возможность произвольного `from/to` и размер выборки следует проверить по актуальной официальной документации и одному разрешенному read-only запросу на архивном интервале, затем сверить границы/единицы/сумму частей. В этом исследовании такая проверка у действующего аккаунта не выполнялась. Не внедрять неиспытанный параметр как якобы поддерживаемый.

При наличии точных неперекрывающихся интервалов измерений связывать их с единственным подтвержденным водителем/машиной. Не делить дневные километры пропорционально часам, выручке или числу заказов: это оценка, а не измерение. При суточной детализации допустима атрибуция только всего измеренного интервала, полностью и однозначно покрытого подтвержденным назначением; в остальных случаях оставить показатель автомобилю и показать нераспределенный остаток. Моточасы/движение/длительность интервала остаются отдельными полями, а не тремя синонимами рабочих часов.

Предложенные точки расширения: отдельная таблица/модуль фактических интервалов, стабильные каталоги `workspace`, отчет водителей, отдельный адаптер interval telemetry рядом с `monitoring_history` без разрушения текущего суточного кэша. Существующие денежные отчеты, часы заказов и машинная сверка работают независимо от заполнения смен.

Приемка: водитель меняет две машины; машина меняет двух водителей; переход полуночи и 27 ч; конфликт перекрывающихся назначений и неизвестный участок; сумма распределенных исходных измерений + остаток равна исходному доступному объему без двойного счета; дневная телеметрия без интервалов не превращается в точный водительский факт. Реальная заполненность требует сведений ответственного, а не алгоритмической догадки.

## G09. Разбор рабочих данных существующими средствами

Не создавать заново таблицы карт, расходов, полноты или планов. Уже есть «Контроль → Карты и автомобили / Расходы / Полнота периодов / Качество данных», редактирование назначений и справочники. Предлагается рабочая очередь с причинами и ссылками на существующие формы; улучшение выбора карты из загруженных и preview влияния полезно, но не отдельный обязательный модуль.

Последовательность:

1. В свежем снимке перечислить 88 неназначенных, 2 строки возможного дубля, 1 review. Проверить каждый случай по оригинальной строке/истории изменений. ФИО в колонке машины, «Заменить» и совпадение водитель=автомобиль не дают права угадать госномер. Не удалять оба дубля: подтвердить отдельный рейс/slot либо отмену конкретной записи.
2. Собрать минимальную историю карт: поставщик, карта, автомобиль, начало/конец использования и источник подтверждения. Имя держателя/комментарий карты — кандидат, не доказательство. Существующая валидация запрещает пересечения; preview должен показать число/суммы операций, которые сменят атрибуцию. Связывать только подтвержденный интервал, не всю историю карты автоматически.
3. Внести подтвержденные дополнительные расходы с датой/автомобилем/категорией/документом. Не копировать топливные операции второй раз в расходы. Отсутствие записей означает «расходы не внесены/не подтверждены», а не доказанную нулевую себестоимость; текущий остаток по известным затратам сохраняет свое честное название.
4. Разобрать отсутствующие статусы после августа только по журналу ответственного. Пустой день не становится «Нет заявки» автоматически.
5. Подтверждать полноту плана/факта за действительно проверенный интервал после разрешения спорных записей и G02. Проверять весь заявленный scope, не только выбранную в данный момент машину. Успешный API-запрос сам по себе этого не делает.

Без новых исходных фактов можно завершить интерфейсы/очередь и показать пользователю точный список недостающих полей. Нельзя заполнить реальные деньги/машины/карты вымышленными значениями ради зеленой матрицы. Историческая просьба пользователя прямо различала структуру ввода и фактическое заполнение.

Приемка на fixtures и одном отдельно подтвержденном рабочем примере: датированная карта распределяет подходящие операции ровно раз, соседние даты не затронуты, возврат сохраняет знак; расход не дублирует топливо; спорный план сохраняет происхождение и прежние суммы; остаточная очередь прозрачна; неподтвержденная реальная экономика не объявлена полной.

## G10. Диагностика текущих ошибок и продвижение догрузки

Состояние из 03 — наблюдение 10:26 МСК, не вечный диагноз. Существующие адаптеры сворачивают все `requests.RequestException` в общее безопасное сообщение (`neftm.py:100`, `rosneft.py:69`, `monitoring.py:71`). Из него невозможно честно восстановить, был ли DNS, TLS, proxy, connect timeout или разрыв чтения. Просмотрены только классы ошибок в концах локальных `server.log`, `autonomy-worker.log`, `autonomy-web.log`: релевантных traceback/классов нет, файлы датированы более ранним запуском. Это не доказательство причины. Прямое чтение публичной страницы документации мониторинга тоже не завершилось в пределах таймаута; оно не доказывает, что поставщик недоступен из рабочей среды.

Исполнимый порядок:

1. Снять свежие безопасные `refresh-state`, heartbeat, per-source last success/attempt, catchup pending/current date и занятую lock/job. Убедиться, что старый снимок не сменился успехом. Не запускать параллельно уже идущую синхронизацию.
2. Для конкретного процесса проверить DNS/TCP/TLS к **известному** хосту, используемый proxy/интерфейс и системное время без вывода секретов. Отдельный публичный GET не проверяет договор/учетную запись; успешный ТТ не доказывает тот же маршрут у трех других источников. Не переносить специальный `en0` ТТ всем поставщикам по аналогии.
3. Добавить при необходимости безопасную классификацию исключений: connect/read timeout, TLS, proxy, connect/DNS, HTTP auth/rate-limit/server, parse/schema. Хранить код класса, provider, время/длительность/период, без `str(exception)`, URL-query, headers/body и токенов. Это позволяет последующему одиночному штатному чтению установить причину, не раскрывая доступы.
4. Выполнить разрешенное минимальное чтение проблемного завершенного дня через существующий adapter и его lock. Для auth-ошибки сверять разрешенность текущего доступа, но не менять/сбрасывать реквизиты; для 429 соблюдать retry; для timeout проверить малую порцию; для schema error сохранить старые данные и обезличенную форму ответа. Не выключать TLS verify и не менять глобальную сеть как «исправление» без доказательства.
5. Исправить только найденную причину и повторить тот же день. У спутника проверить, что успешны необходимые metric/vehicle cells, а не только статус внешней job; что ближайшая пропущенная дата продвигается; что поздние исправления не уничтожаются. Сохранять текущие независимые очереди и idempotency.
6. Зафиксировать два последовательных цикла с per-source результатом, затем изолированный тест прерывания/восстановления и отсутствие дублей. Реальный backlog должен уменьшаться или иметь конкретный внешний блокер; один heartbeat не является приемкой интеграции.

Публичная [документация ГЛОНАССсофт](https://glonasssoft.ru/wiki/metody-api-dlya-raboty-s-glonasssoft) просит не формировать более трех отчетов одновременно. Поэтому «ускорить догрузку» не означает снять существующие ограничения и отправить все 28 дней параллельно. Если одна неисправная дата систематически блокирует очередь, допустим отдельный подтвержденный алгоритм retry/backoff с сохранением проблемной даты и обслуживанием других дней; вводить его только после воспроизведения, не выбрасывая дату из pending.

Приемка: безопасная причина или актуальное подтверждение восстановления для каждого из трех источников; предыдущие данные сохранены при любой ошибке; результат повторной загрузки идемпотентен; источники независимы; 28-дневный backlog не объявлен закрытым до получения проверенных порций. Если внешний источник реально недоступен, отчет точно называет проверенный предел; код «с повторами» не изображает восстановление поставщика.

## G11. Общий сервер

Сохранять готовые `deploy/fleet-web.service`, `fleet-worker.service`, `fleet-alerts.*`, `preflight.py`, `backup.py`, `nginx.example.conf` и `docs/server-autonomy-20261030/DEPLOYMENT.md`. Новый параллельный серверный framework не требуется.

Нужный вход для активации: конкретный Linux/systemd хост, согласованный домен/HTTPS и владелец доступа, постоянный каталог данных, желаемое начало исторического охвата, действующие способы доступа к поставщикам с этого хоста. Сначала искать уже согласованные параметры в проекте; отсутствие домена в данном пакете не разрешает выбрать сторонний сервер. Mac со службой остается локальным хостом и выключается вместе с компьютером.

Перед переносом получить согласованный SQLite snapshot через существующий backup API, отдельно учесть JSON-истории топлива/спутника, очереди и настройки; одного файла SQLite недостаточно. Официальный [SQLite Online Backup API](https://www.sqlite.org/backup.html) предназначен для согласованной копии работающей БД. Не восстанавливать старую базу поверх более новых рабочих изменений. Специальный macOS `en0` не переносить на Linux; preflight уже это защищает.

Приемка после конкретной установки: согласованный HTTPS, web и worker отдельными процессами, запуск после reboot без браузера, health/источники различены, восстановление backup на изолированной копии, прерывание/догрузка/нет дублей, внешние сообщения лишь при G12. До наличия хоста может быть готов deployment-пакет, но нельзя написать «размещено».

## G12. Внешние предупреждения

`app.alerts`, `app.alertwatch` и `deploy/fleet-alerts.timer` уже поддерживают путь уведомления; `alerts-config.json` не настроен. Не создавать вторую систему и не выбирать получателя из случайного адреса/упоминания в старом документе.

Подготовить конкретные варианты конфигурации выбранного пользователем транспорта: Telegram chat ID + локально защищенный bot token либо SMTP endpoint/отправитель/получатель/секрет. Не отправлять каждую минуту сообщение «состояние без изменений».

Проверка полностью выключенного сервера требует внешнего наблюдателя на другом хосте; локальный alertwatch этого не решает. Его создание/подключение — конкретная дальнейшая конфигурация при наличии назначенного канала, не действие нынешнего исследовательского этапа.

Приемка: fake transport проходит сценарии; секреты не попадают в журнал/ответ/Git; после явного назначения канала отдельно подтверждены тестовая доставка и отсутствие лишних повторов. Отсутствие выбранного получателя остается конфигурационной зависимостью, не дефектом кода отправителя.
