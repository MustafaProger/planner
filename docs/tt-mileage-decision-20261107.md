## Официальные основания
- [Установка нового рабочего места](https://tt-net.ru/help/ustanovka_programmy_na_novom_rabochem_meste.html): для облачной базы можно использовать ранее выданный корпоративный комплект либо копию папки коллеги, включая TransTrade.exe, config.set и бланки. Один публичный демо-дистрибутив не является комплектом подключения к рабочей базе.
- [Сервисная утилита](https://tt-net.ru/help/servisnaya_utilita.html): описаны терминальный режим и перенос config.set. Это подтверждает серверное размещение клиента, но не фоновый экспорт.
- [FAQ](https://tt-net.ru/faq/): Windows; для отчетов Word/Excel; лицензии различаются числом одновременно работающих мест.
- [Конструктор](https://tt-net.ru/help/konstruktor_otchetov.html): выбор заявок, шаблона и ручная кнопка формирования; можно выбирать столбцы и Excel-бланк. Команда автоматического запуска в этом разделе не описана.
- [API](https://tt-ok.ru/data/api_doc/): публичный контракт GetOrders не содержит поля километража.
- [База данных](https://tt-net.ru/help/baza_dannykh.html): локальная либо облачная БД. Наличие базы не доказывает доступность поддерживаемого внешнего SQL-интерфейса.

## Варианты
1. Добавление КМ поставщиком в API либо отдельный поддерживаемый endpoint — предпочтительная по сопровождению архитектура, но возможность и сроки не подтверждены. Не задерживать пилот Windows ожиданием ответа.
2. Штатный регулярный экспорт — хорошая схема, если обнаружится команда/настройка в конкретной версии. Пока не подтвержден.
3. Windows-робот — реалистичный следующий эксперимент при отсутствии штатного запуска. Выбирает период, формирует отчет, сохраняет файл и передает его сервису. Нужны Windows-сессия, проверка Excel/диалогов и восстановление после сбоев. Автономность требуется доказать при разрыве RDP, блокировке и перезагрузке.
4. Прямое чтение БД — дополнительный технический кандидат лишь при предоставленном поддерживаемом доступе только на чтение и известной схеме. Не извлекать пароли из config.set и не обещать SQL по одному факту существования базы.
5. Online — возвращаться к нему при демонстрации сохраненного КМ и подходящего способа получения; покупка модуля сама по себе не доказательство решения.
6. Ручной отчет — временная проверка источника и сопоставления, не завершенная автоматизация.

## Предлагаемая схема
Рабочая база ТТ → корпоративный клиент на Windows → отчет с исходными КМ → локальный адаптер/передача по защищенному каналу → проверка и история КМ в CharterStats → отдельное сравнение со спутником.

Предлагается выделенный Windows-сборщик, если действующее рабочее место невозможно держать включенным. Перенос всего CharterStats в Windows не требуется. Для бота проверить наличие свободного одновременного рабочего места и влияние входа на сотрудника; дополнительные покупки заранее не считать необходимыми.

## Пилот и критерии приемки
1. Открыть именно существующую базу и сверить 3–5 заявок с интерфейсом ТТ.
2. Получить отчет с устойчивым ID; если ID не доступен, проверить уникальность номера+даты+машины. Проверить сохраненные КМ, ноль и отсутствие значения.
3. Определить фактический формат файла; добавить адаптер именно к нему.
4. Испытать штатный экспорт или UI-робота. Повтор файла не должен создавать дубли; старый файл не должен затирать новое значение.
5. Повторно выгружать прошлые периоды: заявки и КМ могут вноситься постфактум. Окно и периодичность согласовать с фактической задержкой ввода.
6. Проверить позднюю корректировку/очистку КМ, смену реквизитов, отмену заявки и обычный API-sync.
7. Проверить разрыв RDP, перезапуск Windows, сбой отчета, частичный файл и отсутствие обновления. Показывать давность данных.
8. Сверить ТТ → CharterStats → спутник → разница на реальных машино-днях.
До этих проверок нельзя объявлять автономную загрузку готовой.
